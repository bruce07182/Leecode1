1. From files to databases · a small online store

Imagine you sell coffee online. Amy buys two bags, Ben buys one, and Amy later changes her address. How should your app store customers and orders?

Option A · Plain text file

Simple to start, but the app must read and interpret the lines itself. Updating an address repeated in many orders is error-prone.

102, Amy, Seattle, 50

Option B · JSON file

JSON labels the data, so apps can understand the structure. But a JSON file alone does not automatically provide safe concurrent updates, fast searches, or relationships.

{
  "orders": [
    {"id": 101, "customer": "Amy", "total": 75},
    {"id": 102, "customer": "Amy", "total": 50},

When is a database useful? When many users or processes need to search, update, and connect shared information reliably. Text and JSON remain useful for exports, configuration, APIs, and small datasets.

Brief history · why databases evolved
1950s–1960s · Files

Programs managed records in files. Sharing data across applications was difficult.

1960s · Early database systems

Hierarchical and network databases helped manage related records; IBM's IMS is a well-known example.

1970 · Relational model

Edgar F. Codd proposed organizing data as relations (tables), influencing modern relational databases.

1970s–1980s · SQL and commercial systems

SQL emerged from IBM research and became a standard language for relational databases.

1990s–2000s · Web and open-source databases

MySQL and PostgreSQL became widely used for web applications.

2010s–today · Cloud, distributed and document databases

Managed databases, large-scale distributed systems, and JSON/document storage support different application needs. Relational SQL databases remain widely used.

More · primary keys, foreign keys, indexes and transactions

A primary key identifies a record (customer id 1). A foreign key links an order to that customer (customer_id 1). An index helps certain searches run faster. A transaction groups related changes so they succeed or fail together.

Databases can store JSON; file, JSON, and database are not mutually exclusive choices.

How to design a database · tables and relationships

1. Identify entities: customers, orders, products. 2. Give each table a primary key. 3. Store a customer ID in orders as a foreign key instead of repeating customer details. 4. Pick data types and constraints. 5. Add indexes when queries need them.

Design rule: one fact should generally have one authoritative home. Avoid repeating customer names in every order; use JOIN when you need both.
