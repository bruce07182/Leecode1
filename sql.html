1. Why do we need a database?

Files store information. CSV represents rows and columns; JSON represents structured fields. Both can be saved as files. A database manages information so apps can query, connect and update records reliably.

Each customer is stored once. Orders link to that customer by ID, so changing Amy's information does not require editing every order.

What is SQL, and why use it?

SQL (Structured Query Language) is how we ask a relational database to store, find, change, and connect information. Instead of manually searching files, we write a short command such as SELECT * FROM customers;. SQL is used by apps, websites, and data analysts.

Deep dive · Which databases use SQL?

SQLite: a small database stored in a file, useful for learning, mobile apps, and local tools. PostgreSQL and MySQL: common database servers behind websites. SQL Server: common in business software. Cloud-hosted databases: managed PostgreSQL/MySQL and other SQL services used by web apps. SQL syntax is largely shared, but each system has differences. A web app usually accesses its database through a server/API, not by exposing database credentials in the browser.

Deep dive · other file formats

Plain text: flexible but often requires custom parsing. Fixed-width: fields occupy fixed character positions; common in older business systems. Binary: compact machine-readable records. Indexed/sequential files (ISAM): file organization with indexes for efficient lookups. XML: structured tagged documents. CSV and JSON: widely used for exchange and storage. JSON and XML became popular after relational databases existed, not as historical predecessors.

Deep dive · short database history
1950s–1960s · File processing

Applications stored records in files, often with custom layouts and indexes.

1960s · Early databases

Hierarchical and network systems made related records easier to manage.

1970 · Relational model

Edgar F. Codd proposed a relational approach that influenced modern SQL databases.

1970s–1980s · SQL

SQL emerged from IBM research and became a standard for relational databases.

1990s–today · Web and cloud

Open-source, document, distributed and managed cloud databases grew alongside SQL systems.

Deep dive · keys, indexes and transactions

Primary key: identifies a row. Foreign key: connects orders to customers. Index: speeds up some lookups. Transaction: groups changes so they succeed or fail together.

Deep dive · other ways to access a database

SQL editor: type SQL directly and view results. Application: a website or program sends a request to a backend that reads or updates the database. Database client: a tool connects to a database server and lets authorized users run queries.

Different databases use different connection tools and permissions. You typically need a database address, credentials, and permission to access its data.

Deep dive · programming and web APIs

A typical website sends an authenticated HTTP request to its backend. The backend checks the user's permissions, runs a parameterized SQL query, and returns JSON. The frontend turns the JSON into cards or a table. Never embed production database passwords in browser JavaScript.

GET /api/my-orders
→ Backend checks logged-in user
→ SELECT id, total FROM orders WHERE customer_id = ?
→ JSON: [{"id":101,"total":75},{"id":102,"total":50}]
→ Website displays the orders

How to design a database · tables and relationships

1. Identify entities: customers, orders, products. 2. Give each table a primary key. 3. Store a customer ID in orders as a foreign key instead of repeating customer details. 4. Pick data types and constraints. 5. Add indexes when queries need them.

Design rule: one fact should generally have one authoritative home. Avoid repeating customer names in every order; use JOIN when you need both.
